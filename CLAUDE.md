## Commandes du repo

- `npm run dev` — lance le serveur de dev Next.js.
- `npm run build` / `npm run start` — build de production / lancement.
- `npm run lint` — ESLint.
- `npm run db:generate` — génère une migration SQL à partir de `src/db/schema.ts` (ne nécessite pas de connexion DB active).
- `npm run db:migrate` — applique les migrations en attente sur la base pointée par `DATABASE_URL`.
- `npm run db:push` — pousse le schéma directement sans passer par des fichiers de migration (pratique en dev rapide, à éviter une fois qu'on a des données à préserver).
- `npm run db:studio` — ouvre Drizzle Studio pour inspecter la base.
- `npm run test` — lance la suite Vitest une fois (logique pure + appels Claude mockés, aucune base de données requise).
- `npm run test:watch` — lance Vitest en mode watch.

## Configuration

Copier `.env.example` vers `.env` et renseigner au minimum `DATABASE_URL` (PostgreSQL local) pour que l'app démarre.

Le provider LLM utilisé pour la génération de contenu est sélectionné via `LLM_PROVIDER` — voir `src/lib/llm/`. **Seul `openai` est opérationnel** (`OPENAI_API_KEY`) : c'est la valeur à utiliser, et celle que `.env.example` propose. Les adaptateurs `gemini`, `anthropic` et `groq` existent dans le code mais ne sont pas opérationnels — ne pas compter dessus pour faire tourner l'app (le fallback codé en dur dans `src/lib/llm/provider.ts` reste `gemini` si la variable est absente). `GEMINI_API_KEY` reste nécessaire pour le captioning vision des photos, indépendamment de `LLM_PROVIDER`. Le **détourage** des photos (optionnel) demande `BACKGROUND_REMOVAL_PROVIDER=photoroom` et `PHOTOROOM_API_KEY` (clé `sandbox_` gratuite avec filigrane en dev) ; absent, la fonction est simplement masquée.

**`OPENAI_MODEL` est le levier de qualité le plus important du produit**, mesuré au banc le 2026-10-21 : à brief et prompt identiques, `gpt-5-mini` rend des posts à rubriques (« Bilan factuel : », « Ce que ça coûte : ») et `gpt-6-luna` rend des histoires, en gardant les détails humains du document source (6 sur 10 contre 2 sur 10). La valeur en place dans `.env` reste `gpt-5-mini` : à trancher selon le coût par post.

Les credentials OAuth (Instagram/LinkedIn/X — TikTok et YouTube ont été retirés avec la vidéo) ne sont nécessaires que pour tester la connexion des comptes sociaux (Module A).

L'onboarding (`/onboarding`, un seul parcours, `docs/SPEC_ONBOARDING_MVP.md`) fonctionne **sans aucun fournisseur OAuth configuré** : la porte « Coller mes notes » crée le compte par email/mot de passe et sert de matière ; les portes GitHub, Notion et Linear n'apparaissent que si leurs variables sont renseignées. L'inscription ne se fait plus sur `/login` (qui ne garde que la connexion et le mot de passe oublié).

L'onboarding développeur (connexion GitHub, dépôts publics comme sujets) demande `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` et `GITHUB_OAUTH_REDIRECT_URI` — une OAuth App créée sur github.com, scope `read:user user:email read:org` uniquement. Optionnel en dev : sans ces variables le bouton GitHub n'apparaît ni sur `/login` ni dans l'onboarding, et le parcours par « Coller mes notes » reste complet. Voir `docs/TECH.md` §8.

**Notion** et **Linear** fonctionnent exactement pareil — porte d'entrée et source de matière — avec `NOTION_CLIENT_ID`/`NOTION_CLIENT_SECRET` (intégration **publique** sur notion.so/my-integrations : une intégration interne ne peut pas être autorisée par d'autres comptes) et `LINEAR_CLIENT_ID`/`LINEAR_CLIENT_SECRET` (scope `read`). Redirect URI à déclarer des deux côtés : `${APP_URL}/api/auth/oauth/<provider>/callback`. Absents, les boutons n'apparaissent pas. Voir `docs/SPEC_CONNECTEURS_ET_SUJETS.md`.

Les emails de service (lien de connexion — il n'y a plus de mot de passe depuis le 2026-10-25, `docs/SPEC_CONNEXION_PAR_LIEN.md` —, premier post, confirmation de suppression de compte) passent par `src/lib/email/` : Brevo (`BREVO_API_KEY`, `EMAIL_FROM` sur un domaine vérifié) ou, par défaut sans clé, le mode `console` qui écrit l'email dans les logs — c'est ainsi qu'on récupère un lien de connexion en local. L'identité de l'éditeur des pages légales vit dans `src/lib/legal/publisher.ts` (placeholders tant que l'entité n'est pas arrêtée ; la bannière « en cours de finalisation » disparaît d'elle-même une fois le fichier rempli). Voir `docs/SPEC_LEGAL_EMAIL_RGPD.md`.

Les chiffres des posts (écran Performance, `docs/SPEC_PERFORMANCE.md`) : LinkedIn par l'API officielle une fois l'accès « Community Management API » obtenu (validation LinkedIn, non self-serve) ; **X par Apify** (`APIFY_TOKEN`, `APIFY_X_ACTOR`, `X_METRICS_PROVIDER` = `apify` | `x_api`) à partir du pseudo X saisi dans les réglages, sans connexion OAuth de X. Absents, l'écran reste vide avec un message explicite — rien ne casse.

L'écran `/admin/quotas` (quotas personnalisés par compte) n'est accessible qu'aux emails listés dans `ADMIN_EMAILS` (séparés par des virgules, lu au démarrage du serveur) ; vide, personne n'y a accès. Voir `docs/SPEC_QUOTAS_ADMIN.md`.

La facturation self-service (Stripe) est optionnelle pour faire tourner l'app en dev : sans `STRIPE_SECRET_KEY`/`STRIPE_PRICE_*`/`STRIPE_WEBHOOK_SECRET`, tout utilisateur reste sur l'essai gratuit (5 scripts à vie) et les routes `/api/billing/*` échouent explicitement si sollicitées. Pour tester le flux complet en local : `stripe listen --forward-to localhost:3000/api/billing/webhook` (Stripe CLI) fournit le `STRIPE_WEBHOOK_SECRET` à utiliser. Voir `docs/TECH.md` §6.
